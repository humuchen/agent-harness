三、P0 问题（公网暴露前必须修复，共 3 项）

P0S1 · web_fetch 默认全放行含私网，构成 SSRF 攻击链

backend/core/src/builtins/webfetch.ts:59-84
白名单为空即全放行；私网校验仅在可选 networkPolicy 存在时执行，而 harness 默认透传 undefined。注：DNS rebinding 防护机制（resolveHostIsPrivate 解析级校验 + 连接时二次校验）已落地且部署级开关 GUARDRAIL_ALLOW_PRIVATE_NETWORK=false 可收紧，但缺省值 allowPrivateNetwork ?? true 仍为放行——模型被 prompt 注入操控后可直接 fetch http://169.254.169.254/ 云元数据或内网服务并回传内容。
修复：翻转缺省值为 false（或生产配置强制注入 GUARDRAIL_ALLOW_PRIVATE_NETWORK=false），需要内网访问的部署显式开启。

P0S2 · 密码重置凭证直接在 HTTP 响应中返回，可接管任意账户（含 admin）

access/server/src/routes/account-routes.ts:379 · accounts.ts:1071
POST /api/account/forgot-password 仅受 20 次/分钟限流，响应直接携带一次性 resetToken；攻击者凭用户名即可重置任意账户密码并吊销其全部会话。代码注释自认是演示行为，但生产未封堵。
修复：resetToken 改为邮件/短信带外下发；接口统一返回 {ok:true}；config-schema 校验阻断演示模式上生产。

P0S3 · promtail 挂载 docker.sock，等同授予宿主 root 权限

docker-compose.monitoring.yml:130
:ro 仅限制 socket 文件本身，通过 Docker API 仍可创建特权容器、读宿主任意文件；监控栈一旦被攻破即链式逃逸至宿主机。
修复：改用 docker_sd 只读发现代理方案，或至少 internal: true 网络且不暴露端口。

四、P1 问题（重要缺陷，共 18 项）

backend/core

P1C1 · web_fetch 整包读入内存，OOM DoS

builtins/webfetch.ts:81-84
resp.text() 无字节上限先整包入内存再截断，且截断上限 max_bytes 来自 LLM 参数、无上限校验。修复：流式读取 + 硬上限中断。

P1C2 · multi-key 故障转移冷却逻辑失效

llm/multi-key.ts:55-64
markDead 条件 deadUntil === 0 在首次冷却过期后恒为假，死 Key 每次请求都被轮询（先付必败 round-trip），直到进程重启。修复：条件改 deadUntil <= Date.now()。

P1C3 · 异步 scorer 打分无 catch，rejection 直接炸进程

memory.ts:589-593
void scores.then(...) 无 .catch，插件 scorer 抛错即触发 unhandledRejection（Node ≥15 默认 crash），且位于 memory.add() 热路径。

P1C4 · workflow 引擎并发护栏存在 TOCTOU

workflow/engine.ts:334-341
get→save 之间的 await 间隙允许同 def 并发 run 互相覆盖检查点，step 状态踩踏、resume 失效。修复：原子占位（ON CONFLICT / 文件锁）。

P1C5 · 补偿失败被标 compensated，永不重试

workflow/engine.ts:559-562, 666
补偿执行失败仍标 compensated，resume 视其为终态跳过——副作用既没回滚也不会补执行。修复：引入 compensate-failed 状态并纳入 resume 重试。

P1C6 · shell 工具只锁 cwd 不约束 args，白名单含解释器即逃逸

builtins/shell.ts:152
node -e "…rmSync…" 可读写任意路径，白名单+三道闸门形同虚设。修复：含 -e/-c 的解释器参数强制走 container/os 执行器。

access/server

P1V1 · GET /api/errors 未鉴权，内部错误明细公开

routes/edge-routes.ts:117-137
位于 guard 之前的 edge 路由，匿名可拉取含堆栈/内部路径的错误列表；同功能 HTML 页反而正确做了 guard。修复：移入 guard 后并要求 errors:read。

P1V2 · GET /api/uploads/:filename 无鉴权 + 可执行类型内联回显

routes/upload-routes.ts:71-86
仅上传有 guard，读取完全公开；白名单含 text/html/image/svg+xml 且内联输出，构成登录用户间的存储型 XSS。修复：GET 纳入 guard；移出可执行类型；SVG 加 CSP: sandbox 或强制 attachment。

frontend

P1F1 · 插件视图 HTML 未经净化直接 unsafeHTML 注入主文档

frontend/webapp/src/app.ts:1186 · plugin-ui-registry.ts:39-41
核心聊天管线净化扎实，但插件视图是管线外的裸 sink——任一插件数据被污染即在主应用源上获得 XSS。修复：过 DOMPurify 或改 sandboxed iframe。

P1F2 · refresh token 明文落 localStorage 且登出永不清理

login.ts:1703-1704 · api.ts:40-43
与 F1 叠加即成完整攻击链；注释声称 HttpOnly cookie 与实现矛盾。修复：改 HttpOnly cookie，至少 clearSession() 同步移除。

plugins / rag / mobile

P1P1 · /leads 无鉴权返回全量客资（手机号/微信明文）

plugins/medical-aesthetics-lead/src/server/routes.ts:78-82
同数据面 /assist/briefing 做掩码、/reveal 要管理令牌，此处却裸奔，自相矛盾。修复：读接口统一 denyUnlessAdmin。

P1P2 · leadId 完全信任 LLM 输出，客户消息可注入污染任意客资档案

tools/capture.ts:27 · prompts.ts:79
外部客户消息原样进 prompt 且无分隔标记，提示词"铁律"是唯一防线；可写入他人档案或对任意 leadId 触发 handoff 骚扰。修复：服务端维护 session→leadId 绑定并强制校验。

P1P3 · RAG 嵌入失败静默降级哈希向量并写缓存，永久毒化语料

services/rag/src/embed.ts:139-143, 213-217
降级向量与真实向量同维度混入，检索质量静默崩塌且无告警；API 抖动恢复后该文本仍永久保持哈希向量。修复：失败重试或标 failed；缓存只存真实结果。

P1P4 · mobile token 明文存储，注释声明与事实不符

mobile/src/plugins/biometric-auth.ts:68-71 · AndroidManifest.xml
注释声称 Keychain/EncryptedSharedPreferences，实际是明文 UserDefaults/SharedPreferences，叠加 allowBackup="true" 可随云备份提取。修复：换 secure-storage 插件；allowBackup 改 false。

scripts / deploy

P1D1 · 恢复脚本直接覆盖活动 SQLite，无完整性校验不停服

scripts/backup-db.cjs:165 · rollback-drill.cjs:225
坏备份也"恢复成功"且已覆盖好库；残留 WAL 被重放到新库造成损坏。修复：校验文件头 + integrity_check、清理 -wal/-shm、要求停服或走服务接口。

P1D2 · compose 默认 0.0.0.0 + 空 ADMIN_API_KEY = 匿名全权 admin

docker-compose.yml:14,32 · tunnel overlay
叠加 tunnel 可直通公网，等于公开全部接口（执行 agent 任务、读写全部数据）。修复：默认绑 127.0.0.1；tunnel 对空凭据 :? fail-fast。

P1D3 · db-migrate 无事务且失败退出码为 0

scripts/db-migrate.cjs:96-127
DDL 半成功无回滚；EKS prod 开启 AUTO 迁移时失败不阻断编排，半健康副本继续接流。修复：BEGIN IMMEDIATE…COMMIT 包裹 + 失败 exit 1。

P1D4 · 备份不等待 WAL checkpoint 且直接拷活动库

scripts/backup-db.cjs:85-96
checkpoint 异步未等待即 close+copy，备份可能页级撕裂不可用，而恢复端无校验能发现（与 D1 叠加）。修复：用 .backup() API 或 VACUUM INTO。

六、值得肯定的亮点

  • core 主循环工程化：unhandledRejection 系统性防御、孤儿 tool_call 协议级收齐、时间预算治理（软截止注入/真实取消/部分产出抢救）三条独立成因分别治本。
  • filesystem 双层路径防护：词法 resolve/relative 之外再做 realpath 上溯比对，覆盖 symlink 逃逸。
  • 前端断线恢复引擎：6 次指数退避 + seq 游标续传去重 + 双层看门狗 + forceFinalizeStuck 兜底「终结帧丢失导致永久挂起」死角；会话切换 seq 守卫与「恢复失败绝不清数据」三级降级贯彻到位。
  • server 统一准入网关：guard() 收敛认证→CSRF→租户→限流→RBAC→审批，authz fallback 明确杜绝 fail-open；RunQueue 看门狗/内存监控/LMOVE 原子领取完整。
  • BYOK 密钥纪律：AES-256-GCM 落库、掩码回显、明文不进 env/日志/持久化 descriptor。
  • 医疗插件硬兜底：预约失败工具层自动落库转人工，把提示词纪律升级为代码保障；webhook HMAC+防重放窗口+恒定时间比较完整。
  • 部署加固：Dockerfile 非 root + HEALTHCHECK + 原生严格模式；k8s seccomp/drop ALL/HPA 锁副本 + Downward API 多副本自检；监控栈 Grafana 口令 fail-fast。
