# 架构评审与演进规划

> 分析对象：`agent-harness` 当前实现（以 `docs/01-architecture/architecture.md` 权威总览 + 代码事实为准）
> 对照基准：当前主流架构方案——模块化单体 / 微服务 / 事件驱动（EDA）/ Serverless(FaaS) / Agent 平台托管（LangGraph Platform 类）
> 判定口径：**适用**（当前形态最匹配）/ **瓶颈**（有明确代码证据的边界）/ **建议**（可落地的演进动作），所有结论基于当前代码，不沿用历史评估的过时评级

> 配套图：[`diagrams/架构演进路线图.svg`](./diagrams/架构演进路线图.svg)（当前分层 → P0/P1/P2 演进目标）

## 0. 结论摘要（TL;DR）

1. **架构定位**：当前系统是 **pnpm monorepo 形态的"模块化单体 + 插件化"AI Agent 运行时**——`backend/core` 框架库 + `access/server` 单进程接入层 + 独立 `services/rag`，业务语义 100% 隔离于 `plugins/`。这是刻意的分层取舍，而非"能力不足"。
2. **对比结论**：六维度综合看，模块化单体在中小团队、私有化交付、快速迭代场景性价比最优；微服务/EDA 的优势（独立扩容、事件重放）在当前规模下收益有限、治理成本高；Serverless 不适合分钟级 agent run；平台托管牺牲自主可控。
3. **核心瓶颈**：不在"能力有没有"，而在四类结构性问题——① 编排表达力（静态 DAG，无动态扇出/time travel）；② Token 成本结构性偏高（全量历史每步重发，压缩/缓存默认关闭）；③ 单进程内存态（记忆/注册表/MCP 连接无法水平共享）；④ RAG 底座薄弱（内存向量库，仅小规模可用）。
4. **演进策略**：**先治理成本与质量，再谈规模；按需服务化而非提前微服务**。P0 做上下文/成本治理与 RAG 升级，P1 做编排表达力与数据层，P2 做插件隔离与事件总线；全部沿用"接口 + 默认实现 + 组合工厂"范式，不破坏 `core` 零业务耦合。

## 1. 当前架构总览

### 1.1 分层结构

```
接入层    access/server (node:http + SSE，routes/ 下 18 个路由模块)
          └─ 鉴权/RBAC、审批工作流、运行队列、MCP 管理、账户/OAuth/BYOK、IM 桥接、计划模式
前端层    frontend/webapp (Vite+Svelte SPA) · frontend/cli · mobile (Capacitor 壳)
编排层    backend/core: router/ · workflow/(DagEngine) · a2a/ · subagent/ · teams/
智能体层  backend/core: agents/ (AgentCard + AgentRegistry + AgentStore)
基座层    backend/core: tenant · policy · quota · audit · sandbox · plugin · feature-flags
执行层    backend/core: harness.ts 主循环 · tools · memory · guardrails(三层) · llm · builtins · skills
底座      services/rag (独立部署) · migrations · deploy/k8s · docker-compose · Prometheus+Grafana
```

依赖方向：`server → core`；`webapp → client → server(/api/v1)`；`cli → client`；`examples → core`；插件经 `plugin-bootstrap.ts` 动态加载，server 不静态 import 任何插件。

### 1.2 关键设计特征（代码证据）

| 特征 | 落地方式 | 代码位置 |
| --- | --- | --- |

## 2. 与主流架构方案对比（六维度）

### 2.1 对比矩阵

| 维度 | **当前：模块化单体+插件化** | 微服务 | 事件驱动 (EDA) | Serverless (FaaS) | Agent 平台托管（LangGraph Platform 类） |
| --- | --- | --- | --- | --- | --- |
| **性能** | 进程内调用零序列化，延迟低；瓶颈在单进程事件循环与 SQLite 单写锁 | 跨网络调用有序列化开销，但热点服务可独立扩容 | 异步吞吐高，但事件链路延迟与顺序保障成本高 | 冷启动延迟，不适合分钟级 agent run | 平台侧性能好，但受控于厂商 |
| **可扩展性** | 纵向为主；横向靠 Redis 队列 + 多副本，但内存态（记忆/注册表/MCP）仍是单点 | 最强：按服务独立扩容、独立部署 | 强：消费者独立伸缩，天然解耦 | 无限伸缩，按调用计费 | 中：平台侧扩容，自定义能力受限 |
| **可维护性** | 包边界清晰、monorepo 统一构建；但 server 单进程内 ~90 个模块耦合 | 契约治理、分布式调试复杂 | 事件溯源可审计，但 schema 演进/幂等/重放治理负担重 | 依赖第三方平台行为，调试困难 | 黑盒化，存在锁定风险 |
| **开发效率** | 高：本地一键跑、热更新、跨层 import 无网络成本 | 中低：跨服务契约、部署流水线、数据一致性 | 中：需定义事件契约与编排 | 低：冷启动慢、状态外置重 | 高（标准场景），自定义扩展受限 |
| **部署成本** | 低：单容器 + 可选 Redis 即可上线（compose/k8s/Render 三选一） | 高：基础设施、服务发现、网关、链路追踪 | 高：消息中间件 + 事件存储 | 中：免运维但厂商锁定 + 长任务计费贵 | 高：平台订阅费 |
| **团队协作** | monorepo 统一 CI/版本/复用，适合中小团队 | 按服务拆分团队、独立交付，需强契约治理 | 需事件架构师角色 | 免运维，但调试协作弱 | 依赖平台能力边界 |

### 2.2 关键差异说明

1. **微服务并非不可替代**：当前 `services/rag` 独立部署已验证"按需服务化"路径。当 RAG、评估、插件宿主成为独立负载与团队时再剥离，远比提前拆分收益高——当前规模下微服务带来的运维与契约成本远超收益。
2. **EDA 的合理切入点**：事件模型（审计/告警/指标/跨实例事件）目前各自落盘 + Redis pub/sub，规模化后需要统一事件总线（Kafka/NATS 可选后端）承载持久化重放；但**不要**把主循环改成事件驱动——agent run 是有状态长任务，同步编排语义更简单可靠。
3. **Serverless 明确不适用**：单次 agent run 是分钟级有状态任务（最大 24 步、5 分钟看门狗），冷启动 + 状态外置的成本与复杂度不可接受。
4. **平台托管是"参照系"而非替代**：LangGraph Platform 类方案在编排表达力与生态上更强（见 `langchain-langgraph-comparison.md` §5），但本项目的核心价值——私有化、BYOK、行业合规护栏、IM 入口、零依赖可离线——正是平台托管无法提供的。

| 场景 | 匹配度 | 依据 |

## 4. 潜在瓶颈（按严重度排序）

| # | 瓶颈 | 严重度 | 代码证据 / 说明 |
| --- | --- | --- | --- |
| 1 | **编排表达力不足** | 🔴 高 | `DagEngine` 静态 DAG：无运行期动态扇出（无 Send 式原语）、无 subgraph 嵌套复用、无 time travel、无 step 级 retry/cache/timeout 声明（`backend/core/src/workflow/`，对比 `langchain-langgraph-comparison.md` §5.1） |
| 2 | **Token 成本结构性偏高** | 🔴 高 | 全量历史每步重发 O(steps²)；`CONTEXT_COMPRESSION` / `PROMPT_CACHE` / `MAX_TOOL_RESULT_CHARS` 均**默认关闭**（`backend/core/src/harness/`、`runner.ts`、`memory.ts`），生产未显式开启则成本失控 |
| 3 | **单进程内存态瓶颈** | 🔴 高 | 记忆、`AgentRegistry`、MCP 连接、`ApprovalPolicy` 均为进程内状态；多副本下每实例重复加载，水平扩展仅覆盖任务队列（`access/server/src/run-queue.ts` 已解耦，但其余内存态未解） |
| 4 | **RAG 底座薄弱** | 🔴 高 | `services/rag` 用 HashEmbedding + 内存 JSON 向量库 + BM25/MMR，仅适合小规模；无生产级向量库（pgvector/Milvus/Qdrant）、无 embedding 模型管理、无文档分块管道（`services/rag/`、`docs/07-rag/external-rag-design.md`） |
| 5 | **数据层天花板** | 🟡 中 | 默认 SQLite 单写锁、无读写分离、无跨地域；turso/mysql/pg 可切换但迁移工具链（`scripts/db-migrate.cjs`）与运维实践未跟上（`backend/core/src/db-adapter.ts`、`docs/02-deployment/database-backends.md`） |
| 6 | **插件隔离弱** | 🟡 中 | Node `require` 动态加载，插件与宿主同进程——插件崩溃/内存泄漏可拖垮 server，无资源配额、无类型边界（`access/server/src/plugin-bootstrap.ts`、`plugin-ext.ts`） |
| 7 | **事件模型单体化** | 🟡 中 | 无消息总线：跨实例事件靠 Redis pub/sub；审计/告警/指标各自落盘（`audit.ts`、`errorlog.ts`、`telemetry.ts`），规模化后（多业务域/多消费者/持久化重放）不够 |
| 8 | **可观测性默认关** | 🟡 中 | OTel 可选、指标以内存快照为主，无默认全链路追踪；告警依赖自建 webhook 集成（`telemetry.ts`、`alerting-setup.ts`） |
| 9 | **移动端非原生** | 🟢 低 | Capacitor 仅包裹 webapp，无离线任务调度、无原生能力深度集成（`mobile/`） |
| 10 | **测试与评估工具链薄** | 🟢 低 | 无评估数据集/回归体系，仅 `services/rag/eval.ts` 局部覆盖；LLM-as-judge 无默认实现（`access/server/src/eval.ts` 有接口但缺默认 LLM 评估器） |

## 5. 演进方向与目标

> 总原则：**接口不变、实现可替换**——沿用"接口 + 默认实现 + 组合工厂"范式；**先治理成本与质量，再谈规模**；**按需服务化而非提前微服务**。

### 5.1 重点优化模块（按优先级）

| 优先级 | 模块 | 改进动作 | 落点（沿用现有抽象） |
| --- | --- | --- | --- |
| **P0** | 上下文与成本治理 | 默认开启 `CONTEXT_COMPRESSION=heuristic` + `PROMPT_CACHE`；工具结果按 token 截断（默认 16000 字符过大，按任务类型动态）；新增分层记忆（热窗口/温摘要/冷归档）；重试 token 用量已在 `llm/shared.ts` 累计，扩展为成本告警阈值 | `MemorySummarizer` 契约（已支持异步）、`memory.ts` 窗口机制、`harness.ts` 主循环 |
| **P0** | RAG 服务 | 换生产级向量库（pgvector 起步，预留 Milvus/Qdrant 接口）；引入 embedding 模型管理（模型版本、失败回退）；补文档加载/分块管道；RAG 独立扩缩容 | `services/rag` 的 `Retriever`/`Ingest` 接口、`RAG_EMBED_TIMEOUT_MS` 已有超时自愈 |
| **P1** | 工作流编排 | 补 Send 式动态扇出原语、subgraph 嵌套、step 级 retry/timeout 声明；Checkpointer 从 file 快照迁移到可插拔（Postgres/Redis） | `DagEngine`（`backend/core/src/workflow/`）、`WorkflowStore` 接口 |
| **P1** | 数据层 | Postgres 主库（读写分离）+ SQLite 边缘；统一迁移工具链；租户分库分表能力（`TENANT_DATA_ZONE` 延伸） | `db-adapter.ts` + `db-dialect.ts`（方言层已就绪） |
| **P2** | 插件运行时 | 插件进程外隔离（子进程/容器/WASM），资源配额（CPU/内存/调用数），插件契约版本化与类型校验 | `PluginLoader` 接口（`backend/core/src/plugin/`）、`plugin-bootstrap.ts` |
| **P2** | 运行队列与事件总线 | 事件总线抽象：Redis pub/sub → Kafka/NATS/Pulsar 可选后端，持久化事件重放，审计/告警/指标统一事件流 | `QueueBackend` 接口（`queue-backend.ts`）+ 新增 `EventBus` 接口 |

### 5.2 应引入的架构能力

| 能力 | 现状 | 目标 |
| --- | --- | --- |
| 全链路可观测 | OTel 可选、内存快照 | OTel Instrumentation 默认装配（trace+metrics+logs），服务发现与采样策略可配 |
| 网关与流量治理 | server 内嵌 `guard()` | API 网关（限流/熔断/灰度）承载多业务域流量隔离，保留内嵌降级 |
| 评估与回归平台 | `Evaluator` 接口 + 规则评估器；`LLMJudgeEvaluator` 默认实现已就位（注入 LLM 客户端打分，输出「评分 + 逐条理由」可解析格式，失败/不可解析时回退规则评估并前置降级原因；经 `EVAL_JUDGE_ENABLED` 特性开关门控默认 off，凭据缺失即降级；`Evaluator.evaluate` 允许返回 Promise，`run-queue` 完成门与 `/api/eval` 统一 await） | 评估数据集管理、回归门禁接入 CI |
| 配置与特性治理 | `feature-flags.ts` 进程内 | 远程配置中心（热更新 + 灰度 + 审计） |
| 多地域部署 | `TENANT_DATA_ZONE` 单区 | 多区域部署 + 就近路由 + 数据主权分区合规 |
| 移动端原生能力 | Capacitor 壳 | 原生模块桥接（后台任务、推送、离线队列），Capacitor 仅作过渡 |

### 5.3 衡量改进效果的标准

| 类别 | 指标 | 目标示例 |
| --- | --- | --- |
| **性能** | run p95 延迟、并发吞吐、队列积压深度 | p95 延迟下降 ≥30%；队列积压 < 100 |
| **成本** | 单任务平均 token 成本、prompt cache 命中率 | 长对话成本降低 ≥50%（压缩+缓存）；cache 命中率 > 70% |
| **质量** | 评估通过率、护栏拦截率（误报/漏报）、任务成功率 | 评估通过率 ≥90%；误报率 < 5% |
| **可用性** | SLA、MTTR、RPO/RTO | 99.9% 可用；故障恢复 < 15 分钟 |
| **工程效率** | 部署频率、CI 时长、变更失败率 | 部署频率提升 2 倍；核心测试 < 5 分钟 |
| **规模** | 最大租户数、插件数、并发会话数 | 100+ 租户、50+ 插件无降级 |

### 5.4 演进原则与风险控制

1. **保持 core 零业务耦合**：所有改进通过新增后端/适配器/组合工厂实现，不向 `backend/core` 注入业务策略（唯一例外是纯 I/O 安全的原子写加固，见 `store-safety.ts`）。
2. **默认保守、可开关**：成本治理类改动（压缩/缓存/截断）先以环境变量显式开启，验证后再调整默认值，避免破坏现有行为。
3. **降级可用是底线**：新后端（Postgres/Kafka/pgvector）接入必须满足"缺失即降级"，不得引入硬依赖（与 pnpm-workspace 的 `allowBuilds` 放行策略一致）。
4. **文档与代码同步**：每批次落地后更新 `docs/README.md` 导航与 `docs/02-deployment/hardening.md` 总账，保持"文本文档为当前权威"的仓库约定。
