# 分层架构设计说明

> 基于架构图 `docs/05-analysis/diagrams/分层架构-接入-前端-后端工具.svg` 整理。
> 主线：**前端应用层 → 接入层 → 后端工具层**；支撑底座：**基座服务层 / 执行后端层 / 外部集成与基础设施**。
> 设计目标：**职责清晰、层间解耦、易扩展**。

---

## 1. 文档目标与阅读指引

本文档以用户指定的三个"新层"为主轴，自上而下展开，并说明它们如何挂接在三大支撑底座之上。阅读顺序：

1. §3 三条主线层（前端应用层 → 接入层 → 后端工具层）的职责与关键组件；
2. §4 三层如何依赖 / 调用三大支撑底座（基座服务层、执行后端层、外部集成与基础设施）；
3. §5 层间解耦关系与通信协议；
4. §6–§7 关键组件映射表与"易扩展"设计目标的落地方式。

全文使用中文撰写，技术专有名词（如 SSE、RPC、Tool Registry、AgentHarness.run）保留英文。

## 2. 架构总览（分层模型）

系统采用"**三层主线 + 三底座支撑**"的垂直分层模型。自上而下是请求与能力的流动方向，自下而上是依赖与能力的供给方向：

```
┌──────────────────────────────────────────────────────────────┐
│                     前端应用层 (Frontend)                       │
│  Chat UI · 交互组件 · 业务编排/会话管理 · useAgentContext       │
└───────────────────────────────┬──────────────────────────────┘
                                 │  HTTPS / SSE / WS
┌───────────────────────────────▼──────────────────────────────┐
│                      接入层 (Access / Ingress)                  │
│  统一 API 网关 · 路由分发 · 负载均衡 · 协议转换 · 鉴权 · A2A    │
└───────────────────────────────┬──────────────────────────────┘
                                 │  内部 RPC（协议转换后）
┌───────────────────────────────▼──────────────────────────────┐
│                    后端工具层 (Backend Tools)                    │
│  Server Tools(defineTool) · 数据处理 · 第三方调用 · 底层能力封装 │
└───────────────────────────────┬──────────────────────────────┘
                                 │  依赖（能力底座）
┌──────────────┬────────────────┴───────────────┬───────────────┐
│  基座服务层    │         执行后端层               │  外部集成/基础设施 │
│ Base Services│      Execution Backend          │  External & Infra│
│ Registry/    │  AgentHarness.run · Tool Reg ·  │  Redis · OTel ·  │
│ Tenant/Policy│  Memory · Guardrails · LLM 适配 │  K8s · OpenRouter│
│ Quota/Audit │  · MCP · Skills · Verify ·      │  OpenAI·DeepSeek │
│ Obs/Sandbox │  Builtins · Workflow · A2A      │  · MCP生态·RAG   │
│ Plugin/Ret  │  Transport                       │  · 天气/计算…   │
└──────────────┴────────────────────────────────┴───────────────┘
```

核心思想：**上层只定义"做什么 / 怎么呈现"，下层负责"怎么做 / 用什么实现"**。任何一层都可被替换或水平扩展而不波及其他层。

## 3. 三大主线层（自上而下展开）

### 3.1 前端应用层 · Frontend Application Layer

**职责边界**：页面渲染、用户交互、业务编排、会话管理、前端逻辑处理。它是用户唯一可见的入口，**只负责"呈现与交互"，不感知任何后端工具的具体实现**。

关键组件：

| 组件 | 职责 |
| --- | --- |
| **Chat UI 流式聊天** | 对话主界面（Sidebar + Popup），负责流式消息渲染 |
| **交互组件** | Suggestions（建议）、HITL（人工介入）、Thinking（思考过程）、ToolCalls（工具调用可视化）、文件上传 |
| **业务编排 / 会话管理** | 多轮上下文维护、会话状态机、意图编排 |
| **Agent Context 状态共享** | 通过 `useAgentContext` 在跨组件间共享应用状态（会话、运行态、事件流），避免 prop 透传与重复拉取 |

**解耦点**：前端只通过标准协议（见 §5）与接入层通信，所有业务语义（工具、记忆、护栏）均由后端闭合，前端零感知。

### 3.2 接入层 · Ingress / Access Layer

**职责边界**：请求接入、路由分发、负载均衡、协议转换、鉴权。它是系统的"统一门面"，屏蔽后端多副本、多协议、多租户的复杂度。

关键组件：

| 组件 | 职责 |
| --- | --- |
| **统一 API 网关** | 对外暴露 **HTTP + SSE + WebSocket** 单一入口，是前端与系统之间唯一的契约面 |
| **路由分发** | 按 `tenant / intent → handler` 将请求路由到正确的处理链路（对应 `access/server` 的路由表与 `/api/run`、`/api/verify` 等端点） |
| **负载均衡** | 支持多副本水平扩展，无状态接入 |
| **协议转换** | 将外部 REST/SSE/WS 转换为内部 RPC 调用语义 |
| **鉴权** | RBAC 与 `UI_AUTH_TOKEN` 承载令牌校验（保护 `/api/run`、`/api/verify`、`/api/mcp/*`、`/api/env` 等敏感端点；`/api/state` 与静态资源保持开放供健康检查） |
| **A2A 边界** | AgentCard 自注册，支撑多 Agent 协作（Agent-to-Agent） |

**解耦点**：接入层是"协议与策略的边界"。业务策略（鉴权、审批、配额）在此收敛；后端工具层无需关心"谁在调用、用什么协议调用"。

### 3.3 后端工具层 · Backend Tools Layer

**职责边界**：封装通用工具、数据处理、第三方服务调用、底层能力支撑。它是"能力变现层"，把基座提供的原子能力组装成可被 Agent 调用的工具。

关键组件：

| 组件 | 职责 |
| --- | --- |
| **Server Tools（`defineTool`）** | 以 `defineTool` 统一封装业务/通用工具（天气、知识库、计算等），是新增能力的标准入口 |
| **数据处理** | ETL、格式转换、清洗等数据流水线 |
| **第三方服务调用** | 通过 MCP、Env Platform、外部 API 接入第三方能力 |
| **底层能力封装** | LLM 适配器 / Memory / Guardrails 护栏 / Skills / Verify 自检 / Builtins 内置工具——直接复用执行后端层提供的原子能力 |

**解耦点**：后端工具层只"封装与编排"，不重复实现底层引擎。`AgentHarness.run` 等核心编排逻辑下沉到执行后端层（见 §4.2），工具层保持薄而可插拔。

## 4. 三层如何挂接三大支撑底座

三条主线层本身**不包含引擎**，它们的能力全部来自以下三大底座。依赖方向是"主线层 → 底座层"（能力供给自下而上）。

### 4.1 基座服务层 · Base Services

横切支撑，被接入层与后端工具层共同依赖，提供"平台级"能力而非业务能力：

```
Agent Registry · Tenant Service · Policy Engine · Quota Engine · Audit 审计
Observability · Sandbox 隔离 · Plugin 插件市场 · Retention 留存
Routing & Orchestration · Agent Runtime × N
```

- **接入层依赖**：Tenant / Policy / Quota / Audit / Observability 用于鉴权、配额、审计、可观测；Routing & Orchestration 完成 `tenant/intent → handler` 分发。
- **后端工具层依赖**：Plugin 插件市场提供工具/技能的可插拔来源；Agent Runtime 实例由底座调度（×N 多实例）。

### 4.2 执行后端层 · Execution Backend

后端工具层的能力底座，**`AgentHarness.run` 是核心编排入口**（位于 `backend/core`，对外暴露 `async run(userInput): Promise<string>`，内置 `onEvent` 旁路观测通道与 `AbortController` 超时/取消）：

```
AgentHarness.run · Tool Registry · Memory Store · Guardrails 护栏
LLM 适配器 · MCP / Env Platform · Skills 技能 · Verify 自检
Builtins 内置工具 · Workflow 编排 · A2A Transport
```

- **与后端工具层的关系**：`defineTool` 注册的工具进入 **Tool Registry**；运行时由 `AgentHarness.run` 驱动 LLM 循环，按需调用 Memory / Guardrails / Skills / Verify / Builtins，并经由 **MCP / Env Platform** 与外部交互，复杂流程走 **Workflow 编排**，跨 Agent 走 **A2A Transport**。
- **护栏与记忆自动覆盖**：Guardrails 对 input/output 双向治理，Memory 提供长期记忆，均在主循环内自动生效，工具层与主循环零改动即可受益。

### 4.3 外部集成与基础设施 · External & Infra

最底层的能力来源与运行载体：

```
Redis · OpenTelemetry · Harness.io · Kubernetes
OpenRouter · OpenAI · DeepSeek（兼容 API）· MCP 服务生态
知识库 / RAG · 天气 / 计算 等第三方
```

- **承载关系**：Kubernetes 提供运行载体与多副本调度；Redis 作为运行队列/共享状态（多副本水平扩展前提）；OpenTelemetry 提供追踪（可降级）。
- **能力来源**：LLM 适配器对接 OpenRouter（默认）/ OpenAI（failover）/ DeepSeek（兼容 API）；MCP 服务生态、知识库/RAG、天气/计算等第三方经 MCP / Env Platform 接入。

## 5. 层间解耦关系与通信协议

| 调用方向 | 通信协议 | 说明 |
| --- | --- | --- |
| 前端应用层 → 接入层 | **HTTPS / SSE / WS** | 浏览器侧标准协议：REST 走 HTTPS，流式走 SSE，双向实时走 WS |
| 接入层 → 后端工具层 | **内部 RPC**（协议转换后） | 接入层把 REST/SSE/WS 转换为内部 RPC，屏蔽外部协议细节 |
| 后端工具层 → 支撑底座 | 依赖注入 / SDK 调用 | 函数级调用执行后端层能力；执行后端层再对接外部集成与基础设施 |
| 后端工具层 ↔ 外部集成 | MCP / HTTP(S) / SDK | 经 MCP、Env Platform 或外部 API 调用第三方 |

**解耦三原则**：

1. **接口契约先行**：前端只认统一 API 网关契约，后端只认内部 RPC / SDK 契约，层间不共享实现细节。
2. **协议转换集中**：外部多协议在接入层一次性收敛为内部 RPC，后端无需处理协议差异。
3. **能力下沉**：引擎（LLM、Memory、Guardrails、Workflow）下沉到执行后端层，上层保持薄封装，替换底层不影响上层。

## 6. 关键组件映射与职责

| 关键组件 | 所在层 | 职责 | 易扩展点 |
| --- | --- | --- | --- |
| `useAgentContext` | 前端应用层 | 跨组件共享会话/运行态/事件流应用状态 | 新增页面只需消费同一 Context，无需改数据流 |
| 统一 API 网关 | 接入层 | HTTP+SSE+WS 单一入口、路由、鉴权、协议转换 | 新增客户端只接网关，不动后端 |
| `UI_AUTH_TOKEN` / RBAC | 接入层 | 敏感端点鉴权、开放端点健康检查 | 鉴权策略在边界收敛，可独立升级 |
| `defineTool` | 后端工具层 | 工具统一封装入口 | 新增工具=封装+注册，前端零改 |
| Tool Registry | 执行后端层 | 工具注册与分发 | 工具热插拔 |
| `AgentHarness.run` | 执行后端层 | 核心编排入口（LLM 循环、onEvent、超时取消） | 编排逻辑集中，易于增强 |
| Guardrails / Memory | 执行后端层 | 输入/输出护栏、长期记忆 | 自动覆盖主循环，零侵入 |
| LLM 适配器 | 执行后端层/外部 | 对接多 LLM 厂商 | 新增厂商=实现适配器 |
| MCP / Env Platform | 执行后端层/外部 | 第三方能力接入 | 生态可插拔 |

## 7. 设计目标落地：职责清晰、易扩展

本架构把"易扩展"落到 5 个明确切口：

1. **新增工具**：用 `defineTool` 封装 → 注册到 Tool Registry → 经 `AgentHarness.run` 自动可用，**前端无需改动**。
2. **新增客户端**：任何前端/CLI 只要对接**统一 API 网关**（HTTP/SSE/WS）即可，后端无感。
3. **新增 LLM 厂商**：实现 **LLM 适配器** 对接 OpenRouter/OpenAI/DeepSeek 等，主循环不变。
4. **水平扩展 / 多副本**：接入层**负载均衡** + 基座 **Agent Runtime × N** + Redis 共享队列，无状态接入即可横向扩。
5. **新增 Agent / 协作**：通过 **A2A AgentCard 自注册** 接入，跨 Agent 走 A2A Transport，无需改动主线层。

每一层都可被独立替换、独立演进——这正是"职责清晰、层间解耦、易扩展"三目标的体现。

---

## 8. 小结

- **三层主线**：前端应用层（呈现/交互）→ 接入层（网关/路由/鉴权/协议转换）→ 后端工具层（工具封装/数据处理/第三方调用）。
- **三底座支撑**：基座服务层（平台级横切能力）、执行后端层（`AgentHarness.run` 为核心的引擎与编排）、外部集成与基础设施（LLM/Redis/K8s/MCP 等能力来源与载体）。
- **协议**：浏览器侧 HTTPS/SSE/WS；内部 RPC；底座间依赖注入/SDK；第三方经 MCP/HTTP。
- **灵魂**：上层薄、下层厚；接口契约先行、协议转换集中、能力下沉——以最小改动换取最大扩展弹性。
