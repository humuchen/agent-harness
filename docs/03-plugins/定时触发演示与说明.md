# 定时触发演示与说明

> 配套代码：`scripts/cron-run-example.sh`（路线 A）、`examples/scheduled-trigger-plugin.ts`（路线 B）。
> 本文回答一个问题：**agent-harness 没有内置 cron，怎么让 agent 定时跑？**

## 结论

agent-harness 当前**没有内置调度子系统**。定时触发只有两条路：

| 路线 | 机制 | 谁负责周期性 | 重启是否丢任务 | 推荐度 | 适用 |
|---|---|---|---|---|---|
| **A 外部 OS 调度** | 外部 cron / systemd-timer / SaaS 周期性 `POST /api/run` | OS / 外部 | 不会丢（OS 负责） | ⭐⭐⭐ 生产首选 | 固定频率、可容忍秒级误差 |
| **B 进程内自触发** | 插件 `onStart` 里 `setInterval` 调自己 | harness 进程 | **会丢**（进程被杀定时器就没了） | ⭐ 仅演示/轻量 | 脚本内联的轻量轮询，且能接受偶尔漏跑 |

**一句话选型**：生产用路线 A；路线 B 只适合「进程在就轮询、进程没了无所谓」的场景，且必须自己做持久化 reclaim（见下文）。

---

## 路线 A：外部 OS 调度（推荐）

### A.1 cron（最简，单机）

`scripts/cron-run-example.sh` 已封装好「发一次 `/api/run`」的全部细节。注册到 crontab：

```bash
# 每 5 分钟触发一次
*/5 * * * * /path/to/scripts/cron-run-example.sh >> /var/log/harness-cron.log 2>&1
```

脚本已解决三个生产坑：
- **幂等**：`flock -n` 防重叠——上一次还没跑完（模型响应慢）本次直接跳过，绝不重复执行。
- **失败告警**：非 2xx 一律 `exit 1`，cron 会把 stderr 邮寄给 owner（或落到日志被外部告警采集）。
- **JSON 安全**：用 `jq` 构造负载，提示词里的引号/换行不会破坏 JSON。

环境变量：`HARNESS_BASE_URL`、`OPEN_API_KEY`（**注意是 `OPEN_API_KEY` 不是 `UI_AUTH_TOKEN`**——后者不被 authz 消费）、`SCHEDULE_PROMPT`、`SCHEDULE_AGENT_ID`。

### A.2 systemd-timer（现代 Linux 服务，推荐替代 cron）

`/etc/systemd/system/harness-scheduled.service`：
```ini
[Unit]
Description=agent-harness scheduled trigger
After=network-online.target
Wants=network-online.target

[Service]
Type=oneshot
User=ah
Environment=HARNESS_BASE_URL=http://127.0.0.1:4173
Environment=OPEN_API_KEY=xxxx
ExecStart=/opt/agent-harness/scripts/cron-run-example.sh
```

`/etc/systemd/system/harness-scheduled.timer`：
```ini
[Unit]
Description=Run harness scheduled trigger every 5 minutes

[Timer]
OnCalendar=*:0/5
Persistent=true          # 机器关机/休眠错过的时间点，开机后补跑
AccuracySec=1s

[Install]
WantedBy=timers.target
```
```bash
systemctl daemon-reload
systemctl enable --now harness-scheduled.timer
```
`Persistent=true` 等价于路线 B 想要的「重启 reclaim」，且由 systemd 可靠保证。

### A.3 Render 等 PaaS（无 cron）

Render 不直接提供 cron。两种做法：
1. **外部调度器**：用 GitHub Actions（`on.schedule`）/ 任意一台常驻机上的 cron 来打 `/api/run`（推荐）。
2. **Uptime/Health 探测类服务**：部分「定时 ping」SaaS 可周期性请求你的端点（需先把触发逻辑做成一个公开/鉴权的 HTTP 路由，例如插件自带的 `/api/plugins/<id>/tick`）。

## 路线 B：进程内自触发（演示）

见 `examples/scheduled-trigger-plugin.ts`。核心是 `Scheduler` 类：

```
onStart(ctx)
   │
   ├─ 读配置（interval / stateFile / baseUrl / apiKey / prompt）
   ├─ new Scheduler(...)           持久化 lastExecutedSlot 到 JSON
   └─ sched.start(tick)
         │
         ▼
   tick():  now → slot = floor((now-start)/interval)
         │  slot <= lastExecutedSlot ? 跳过（幂等）
         ├─ from = max(lastExecutedSlot+1, slot-catchUpCap+1)
         ├─ for s in [from..slot]:
         │     onTrigger(s): POST /api/run { runId:`scheduled-ping:${s}` }
         │       成功 → 清连续失败计数; 失败 → emit alert
         │     lastExecutedSlot=s   ← 无论成败，本 slot 只执行一次（失败不反复重试）
         │     persist()   ← 每步落盘
         └─ 返回

disable(id) → onStop(ctx) → sched.stop()（clearInterval）
```

### 重启 reclaim（最关键）

Render 重启进程后，`setInterval` 随之消失，已排期但还没执行的 slot 会「消失」。解法：

- `lastExecutedSlot` 落盘（原子 tmp+rename）；
- `onStart` 立即跑一次 `tick()`，把 `startEpoch` 以来的 slot 与磁盘进度比对，补跑所有「未执行」的 slot；
- `catchUpCap` 封顶（默认 10）防止停机很久后一次性雪崩式补跑。

> 示例默认无 server，`POST /api/run` 会 `ECONNREFUSED`——这恰好演示了「失败告警」路径（`ctx.events.emit({type:'plugin:alert'})`，被核心 `emitAlert` 桥接，可被 Webhook/日志 sink 采集）。

### 运行演示

```bash
pnpm -r build
pnpm --filter @agent-harness/examples run scheduled-trigger
# 默认每 2s 触发一次、8s 后自动 stop 退出，期间可见失败告警日志。
```

## 关键注意事项

### 幂等（必须）
- 路线 A：`flock` 防重叠；`runId` 建议带时间戳/UUID，server 端若支持按 `runId` 去重则双重保险。
- 路线 B：用「slot 序号」作为执行键，同一 slot 绝不重复执行；`runId` 编码 slot 天然幂等。

### 失败告警（必须有）
- 触发失败（网络/鉴权/5xx）要暴露出来：路线 A 靠 `exit 1` + 外部采集；路线 B 靠 `ctx.events.emit({type:'plugin:alert'})`。
- 建议同时记录**连续失败次数**，连续 N 次后升级告警（示例中已累计 `consecutive` 字段）。

### 时区（最易踩坑）
- **interval 模式基于 epoch 毫秒，与时区无关**——「每 2 小时」永远正确，但「每天 09:00 北京时间」用 interval 实现不了（会随 UTC 漂移）。
- 需要「每日定点」时，改用 cron 表达式（路线 A 的 systemd `OnCalendar=*-*-* 09:00:00` 或 cron `0 9 * * *`）或时区感知的 `nextRunAt` 计算，而不要用 `setInterval`。
- 涉及「本地时区」的定时，**永远在调度器侧确定好绝对时间再下发**，不要让模型/agent 自己猜时区。

---

## 选型建议（收尾）

1. 生产定时任务 → **路线 A**（cron / systemd-timer / 外部 SaaS），把周期性和可靠性交给 OS。
2. 只在「进程存活期间做轻量轮询、漏跑可接受」时用路线 B，且务必带上本文的持久化 reclaim + 失败告警。
3. 若未来需要「平台内托管 cron」，正确做法是新增一个**调度服务/插件**，由它持有定时器并复用路线 A 的 `/api/run` 调用，而不是把 cron 语义塞进核心 runtime。
