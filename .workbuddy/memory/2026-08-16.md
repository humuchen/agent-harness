## 真实模型调用无打字效果 — 根因与修复（第二轮）

用户用真实 OPEN_API_KEY 测试：**真实大模型输出不是打字效果，而是等一下整段显示**。

根因定位（实测 SSE 抓包确认，非臆断）：

- 真实 LLM 适配器本身支持流式（`stream:true` + 逐 delta 回调 `onToken`），harness `streamTokens` 默认 true 也确实透传。**后端链路正确**。
- 但本环境默认模型是 `agnes-2.5-flash`，base URL `https://apihub.agnes-ai.com/v1`（OpenAI 兼容代理）。它虽接受 `stream:true`，却把**整段回复缓存在最后一个 delta 一次性吐出**——实测：1 条 `llm:token`（含全文本）+ 1 条 `llm:response` + 2 条 `run:end`（均带 `final` 全文），中间无增量。
- 旧前端 `ingest` 收到 `llm:token` 直接 `patch({content: c.content + delta})`：单条大 delta 一帧跳到全文 → 看不到打字。mock 之所以能打字，是后端用 `setTimeout` 把小 delta 拉开间隔，与 `streamTokens` 无关。

修复（`packages/webapp/src/chat.ts`，纯前端，后端无需动）：

1. 新增打字机缓冲 `pendingContent` / `pendingReasoning`：`llm:token` / `llm:reasoning` 不再直接进 content，而是进缓冲。
2. `ensureTypewriter()` 起 24ms interval，`tickTypewriter()` 按 **自适应步长** `typeStep(n)=min(28, max(2, ceil(n/70)))` 逐段揭示：缓冲小（真流式）→ 2 字/tick 自然打字；缓冲大（单条大块）→ 随长度加速但封顶 28 字/tick，保证长文 ~1.5s 内揭示完。
3. **关键**：`run:end` 不再用 `final` 覆盖 content（否则整段秒显），仅记录 `finalContent` 兜底；`finally` 改用 `drainTypewriter()`——停掉 interval、按同样节奏把剩余缓冲揭示完，仅当打字机全程零可见文本（空 delta 边缘情况）才用 `final` 补。
4. 切换/新建会话、`abort` 时 `flushTypewriter()` 立即落盘，`stopTypewriter()` 清理定时器，防缓冲泄漏。

验证：

- 算法仿真（Node 复刻 typeStep+tick）：50 字经 25 tick、155 字经 75 tick 渐进揭示，最终完整 → PASS。
- `tsc --noEmit` + `vite build` 通过，新 bundle `index-DZMbZKO7.js`；服务端实时托管、含全部打字机符号。
- 真实调用 SSE 仍只有 1 条大 token（端点行为不可改），但前端缓冲后逐字揭示 → 打字机对真实模型生效。

**结论**：真实代理一次性吐全段的限制只能在**前端用打字机缓冲**解决，无法靠改后端流式代码绕开。

## 深度思考展示真实思考内容 — 根因（第四轮，重大）

用户报「深度思考展示的不是无关紧要的步骤，需要把模型思考的内容展现出来」。第三轮我错误地用从调用链派生的「过程解析」兜底（用户认为无关紧要），第四轮需让 深度思考 真正展示**模型真实思考**。

### 真正的根因（用代理抓包定位）

1. **模型思考字段名是 `reasoning_content` 而非 `reasoning`**：`agnes-2.5-flash`（base `https://apihub.agnes-ai.com/v1`）以 OpenAI o1 风格 `delta.reasoning_content` / `message.reasoning_content` 返回思考，而 `shared.ts` 原只读 `delta.reasoning` → 永远抓不到。
2. **适配器丢弃了流式回调（最致命）**：`openRouterLLM` / `openaiLLM` 调 `callOpenAIChat` 时**只透传 `signal`，漏传 `onToken`/`onReasoning`** → `callOpenAIChat` 因 `!(onToken||onReasoning)` 永远走**非流式分支** → 流式路径从不执行 → `llm:reasoning` 永不发射，`llm:token` 仅是 harness 在 `streamTokens` 开启时的「整段兜底」单 token（harness.ts:338）。这就是为什么推理始终丢失。
3. **agnes 流式行为不确定**：即便请求 `stream:true`，有时返回 SSE（`delta.content`/`delta.reasoning_content`），有时返回单条非流式 `chat.completion`（`message.content`/`message.reasoning_content`）。原 `streamOpenAIChat` 只认 SSE，非流式响应整段丢失。

### 修复（core 三处 + webapp）

- `packages/core/src/llm/shared.ts` `streamOpenAIChat`：
  - 读齐全量 `raw` 后分支：非 SSE（无 `data:` 前缀且无 `\n`）→ 按单条 JSON 解析，捕获 `message.reasoning_content`/`message.reasoning` + `message.content` + `tool_calls`。
  - SSE 分支：除 `delta.reasoning`/`delta.reasoning_content` 外，新增 `choice.message?.reasoning_content`/`reasoning` 捕获（最终聚合事件）。
- `packages/core/src/llm/openrouter.ts`：请求体增 `reasoning: { enabled: true }`（agnes 据此流式返回思考；`LLM_REASONING=off` 可关以兼容不识别该字段的 provider）；**并把 `options.onToken`/`options.onReasoning` 透传给 `callOpenAIChat`**（关键修复）。
- `packages/core/src/llm/openai.ts`：同样透传 `onToken`/`onReasoning`。
- `packages/webapp/src/chat.ts` `renderDeepThinking`：深度思考 tab **只展示真实思考**（`m.reasoning`，`parseDeepThinking` 解析 + 关键变量卡 + 随 `pendingReasoning` 打字机），**删除**从调用链派生的「过程解析」兜底（`renderDeepThinkingFromTrace`/`extractKeyVars`/`extractSteps` 一并删除）；tab 出现条件改回仅 `hasReasoning`。

### 验证（真实模型，PID 65394 / 4173，agnes-2.5-flash）

- 简单推理题：`llm:reasoning` 事件 **141** 条，落盘 `reasoning_len:270`（真实思考：「让我一步步分析：前天=星期一 → 昨天=星期二 → 今天=星期三 → 明天=星期四」）。
- 工具调用（"创建 demo-env 预览环境"）：`llm:reasoning` **350** 条 + `tool:start`×2 + trace 完整 → `reasoning_len:777` 与调用链**同时**捕获。
- `tsc` core/server 通过，`vite build` webapp 通过（bundle `index-DN3kKM_k.js` 含 `深度思考`/`dtab-body`）。无遗留 debug 日志。

**结论**：根因是适配器漏传流式回调 + 字段名不符 + 非流式响应未解析。修复后 深度思考 tab 展示模型真实思考内容（打字机），调用/步骤留在「调用链」tab，二者职责清晰分离。

**调试手法沉淀**：agnes 不可靠流式下，用本地 node 代理（`/tmp/llm_proxy.js` 转发 `/v1/chat/completions` 并记录请求体摘要 + 原始响应）是定位「请求到底发没发 reasoning、返回到底是 SSE 还是非流式」的最快手段；比对「代理原始响应」与「harness SSE 事件」可瞬间看出哪一层丢字段。

## 手机端输入框仍需滚动 — 根因（sharedStyles 级联陷阱，20:11）

- 症状：改 `100svh` 后 PC 正常，但手机端输入框仍在折叠线以下、需下拉才能看到。
- **真因**：`sharedStyles`（packages/webapp/src/styles.ts）里 `@media(max-width:760px){:host{height:auto;min-height:100dvh;overflow:visible}}` 会套用到**所有** include 它的组件（含 ah-chat）。我之前只在 chat.ts 移动端 `:host` 覆盖 `height:100svh` + `overflow:hidden`，却**漏了 `min-height`**——`sharedStyles` 的 `min-height:100dvh`（大视口高度）一直生效；因 `dvh > svh`，它把 `:host` 撑到至少大视口高，我的 `100svh` 被顶开 → 仍需滚动。
- 修复：chat.ts `@media(max-width:900px) :host` 补 `min-height:0`，中和 `sharedStyles` 的 `min-height:100dvh`。
- **级联验证（重要）**：`static styles=[sharedStyles, chatCss]`，数组顺序决定源码顺序 → `760px` 块（idx 36623）在 `900px` 块（idx 195437）之前；手机 ≤760px 同时命中两者、同特异性（`:host`），后发的 900px 规则胜出。已确认产物中 `min-height:0`(1) 与 `min-height:100dvh`(1) 并存且 900 在后。新 bundle `index-QHyqb_KV.js`。
- **教训**：凡是 include 了 sharedStyles 的组件，移动端若想锁定 `:host` 为视口高度，必须**同时**覆盖 `height`、`min-height`、`overflow` 三者，否则 sharedStyles 的 `min-height:100dvh` 会悄悄把高度撑开。排查时直接用 `node -e` 读 dist bundle、比对媒体查询 idx 顺序，比肉眼读源码可靠。

## 模型回复结束却一直显示「模型正在回复…」、输入框禁用 — 根因与修复（20:38）

- 症状：模型已输出完最终回答，但交互状态卡在「回复中」，输入框禁用、点不动，无法继续对话。
- **根因（Lit 响应式陷阱）**：`chat.ts` 的 `streaming` 原本是**普通 `private` 字段（非 `@state`）**，run 结束时用 `this.streaming[sid]=false` **对象属性赋值**更新。对象内属性赋值 Lit 完全观测不到 → 不会触发重渲染；而 `finally` 末尾的 `this.messages = this.threads[sessionId]` 与流式末次 `patchSession` 赋的是**同一个数组引用**（引用相等）→ Lit 判定「未变」→ 也不重渲染。于是 UI 永久停在 `streaming===true` 的那一帧，动效不消失、输入框不解锁。
- **修复（`packages/webapp/src/chat.ts`）**：
  1. `streaming` 加 `@state()`，并新增 `setStreaming(sid,val)` 用**不可变重赋值** `this.streaming = {...this.streaming,[sid]:val}` 更新 —— 每次 true/false 切换都触发重渲染。
  2. `send()` 内两处写入（`=true` / `=false`）改调 `setStreaming`。
  3. `ingest()` 顶部拦截终结事件 `run:end`/`_done`/`error`，立刻 `setStreaming(sid,false)` —— 即便 SSE 连接因故迟迟未关闭，UI 也会在最终答复到达时即时解锁；`finally` 中的 `setStreaming` 为二次兜底。
- **教训（可复用）**：Lit 里把 `Record`/`Array` 等作为状态且需要响应内部变化时，必须用 `@state` + **整体不可变重赋值**，绝不能 `obj[key]=val` 直接改属性。用 `node -e` 读 dist bundle 确认 setStreaming 与终结事件重置已落地。新 bundle `index-s7NNEb2i.js`。
