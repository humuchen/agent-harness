## UI 测试诊断：闭环提前结束 + token 消耗大（用户反馈，根因定位）
- **现象1 复杂任务闭环直接结束**：根因两条。
  - 出口A：`maxSteps` 默认 **12**（`packages/core/src/harness.ts:76`），且 `runner.ts assembleAgent` 未透传 `maxSteps`（UI 也无入口）→ 复杂任务 >12 步时返回 `'[agent] reached max steps without a final answer'`（`harness.ts:286`），用户误以为完成。
  - 出口B：唯一终止条件是「LLM 不再返回 tool_calls 即 `return resp.content`」（`harness.ts:239`）；模型一旦返回文本/反问/空响应（含 `shared.ts` 退化响应重试后仍空）即结束，**无完成校验/自我修复**。弱模型复杂任务常触发。
- **现象2 token 消耗大**：结构性，非偶发。
  - 每步 `memory.history()` **全量重发**（`harness.ts:179`）→ 累计 prompt tokens ≈ O(步数²)；工具原文（web_fetch/文件/MCP 输出）逐字存 `tool` 消息（`harness.ts:278`）并被后续每步重发，无截断/摘要。
  - 系统提示词（base + 全量 `skillCatalog` + `skillBoost`，`runner.ts:224`）每步重发，无 prompt caching（`cache_control`）。
  - **跨 run 放大**：若 `MEMORY_BACKEND=sqlite/file`（持久化开启），`harness.ts:132` `memory.load()` 把该会话之前所有 run 的历史+工具输出全部载入并随新 run 重发 → 多轮对话 token 乘倍。默认 volatile 则每 run 独立、不跨 run 累积。
  - `maxWindow=20`（`memory.ts:32`）滑动窗口阀值高，复杂 12 步 run 才可能在末尾截断，且截断会丢最早的 user 请求/系统提示（系统提示被丢后 `harness.ts:147` 守卫会再次注入 → 重复）。
  - `callOpenAIChat` 默认重试 2 次（`shared.ts:67`）+ 退化响应重试，每次重试重发全量 prompt，免费/弱模型抖动时进一步放大成本。
- **建议（待用户确认是否动手）**：① `maxSteps` 提到 20~30 或 UI 可配；② 加完成自检（模型声明 done 前校验）；③ 工具输出截断/摘要；④ 上下文压缩（early turns 摘要）+ 真正按 `maxWindow` 裁剪；⑤ prompt caching；⑥ 持久化开启时按 run 分段、不直接整体重发历史；⑦ 重试与退化响应计入 token 预算。

## Render 部署踩坑：frozen-lockfile 安装失败（ERR_PNPM_OUTDATED_LOCKFILE）

- **踩坑**：① `accountModel` 在 runner 中声明晚于压缩逻辑使用 → 上移到 `maxWindow` 之后；② `LLM` 契约 `tools` 参数必填 → `createLLMSummarizer` 调用补 `llm(messages, [])`（适配器对空 tools 不发送 `tools` 字段，安全）；③ 异步失败回退时摘要槽仍保留，窗口会比 maxWindow 少 1（有意的防溢出预留）。

## 企业落地就绪度评估（用户问"整个项目到企业落地是不是已经可以实现了"）
实测代码（非仅 README）后的结论：架构与多数企业特性**真实落地**，可部署/可当中小团队底座，但**尚未是开箱即用企业级产品**。
- **已就绪（生产级，实测）**：核心 agent 循环/护栏/三层注入+PII 脱敏；多租户记忆 `SqliteMemoryStore`(node:sqlite 真实实现)+File+Volatile；运行队列 `RedisQueueBackend`(ioredis 已装、LMOVE 原子 claim/reclaimStale/pubsub 真实)；RBAC(token级,admin/operator/viewer)+审批(InMemory)；审计日志+脱敏；密钥外部化(3 源,平台 env 优先)；可观测性/metrics/告警接收器；评估+配方版本化；留存窗口+出境 PII scrub；/api/v1 版本化+OpenAPI；上下文压缩(heuristic/llm)+成本预算熔断；CI(构建+测试+audit+SBOM+dependency-review,但 audit 非门禁)。
- **接口已留、实现待补（真实缺口）**：① **SSO/OIDC/LDAP 未实现**——RBAC 仅静态 token，无用户目录/令牌轮换（`createAuthorizer` 注释说"只改工厂"但无实现）；② **harness-env-platform 后端不在本仓库**——自助环境治理闭环目前是 dry-run 客户端(`harness-client.ts` 默认 dry-run)，无真实后端则"创建/销毁环境"能力不可交付；③ 多租户仅有 sessionKey 隔离，无租户开通/配额/账单。
- **完全缺失的交付物**：无 Dockerfile、无 K8s/Helm、render.yaml 仅单实例 free 计划(oregon)；无生产级 HA/ingress/密钥管理接入；依赖安全审计非阻塞门禁；无 SOC2/GDPR 等正式合规模块（仅有基础留存/脱敏骨架）。
- **建议**：对外宣称"企业落地就绪"前，至少补齐 SSO、harness-env-platform 后端(或明确该能力为外部依赖)、Docker/K8s 交付物、把 audit 转为门禁。否则定位为"可部署的强骨架 + 内部 Playground"更诚实。

## Render 部署 `pnpm install` 连环失败（根因 = lockfile 漂移，已自愈化）
- **现象**：Render 构建 `pnpm install` 报 `Command failed with exit code 1`，wrapper 包住真实错误；这是**第三次**同类失败。
- **真实根因链**：`render.yaml` `buildCommand: pnpm install --frozen-lockfile && pnpm -r build`；pnpm 在 CI 环境（CI=true）默认强制 `--frozen-lockfile`，**lockfile 与 package.json 不一致即 exit 1**。本项目每次给 workspace 包加依赖都忘了重新生成 `pnpm-lock.yaml` → 漂移 → 部署卡死。
  - 第 1 次（ioredis，commit 2ee380b 后）：`packages/ui` 加可选依赖 `ioredis@^5.4.1`，lockfile 未同步。
  - 第 2 次（本次）：`packages/core` 加可选依赖 `@kubernetes/client-node@^0.22.0`（commit 32d4d36 环境平台可插拔化/k8s 后端），lockfile 未同步。复现真实报错：`[ERR_PNPM_OUTDATED_LOCKFILE] ... not up to date with packages/core/package.json / 1 dependencies were added: @kubernetes/client-node@^0.22.0`。
- **Render 部署分支确认**：`render.yaml` 注释 + `origin/HEAD -> origin/main`，但部署实际选 **dev 分支**（`render.yaml` 顶部注释 `branch: dev` / `Select the branch ... (dev)`）。dev tip 32d4d36 含 k8s 漂移；origin/main 较旧（无 k8s）。两分支各自 lockfile 在各自 package.json 视角下此前已自洽，但 dev 的 k8s 提交漏了 lockfile。
- **修复（commit 1756178，已 push origin/dev `32d4d36..1756178`）**：
  1. `pnpm install --lockfile-only` 离线重建 lockfile（沙箱 `pnpm install` 被 safe-delete 守卫拦，用 `--lockfile-only` 只更新 lockfile 不下包）；补齐 ioredis@5.11.1 + @kubernetes/client-node 及其传递依赖。
  2. **根治**：`render.yaml` 构建命令改为 `pnpm install --no-frozen-lockfile && pnpm -r build`（显式覆盖 CI 默认 frozen）。此后即便再忘同步 lockfile，Render 构建也能自动校正、不再卡死。
  3. 验证：`pnpm install --frozen-lockfile` 通过（exit 0）；`pnpm -r build` 三个包 Done（exit 0）。
- **复用规则**：① 给任何 workspace 包增删依赖（含 optionalDependencies/devDependencies）后，必跑一次 `pnpm install` 并把 `pnpm-lock.yaml` 一起提交；② CI（Render/pnpm 默认 CI=true）下 `--frozen-lockfile` 会硬验 lockfile，本地复现失败用 `pnpm install --frozen-lockfile` 直接看真因；③ 沙箱内只可用 `pnpm install --lockfile-only` 重建 lockfile（不下包），真安装会被守卫拦截。
